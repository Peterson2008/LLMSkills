# 写算法报告（algorithm-report）

把一次 策略 / 算法 / 模型 的工作，写成**读得懂、且愿意信**的报告。工作有两种形态，都值得记：

- **有收益**：改动上线、指标动了——讲清解决了什么痛点、值多少。
- **只有过程**：做了实验 / 尝试，未必有直接收益——讲清做了什么尝试、**为什么值得试**、结果如何、**沉淀了什么认知**。中间过程也是资产，别因为"没收益"就不记。

> **想看写全的样子** → 读 `references/越送越快.md`（本 skill 自带的完整样例，属"有收益"那一档）。方法论看下面正文；那份样例作"火候"参照——但它通篇的领域细节（指标、术语、维度、案例）只是示范，**别当固定项照搬到别的场景**。

## 读者要什么

- **只关心三件事**：解决 / 探索了什么问题· 你怎么做到的（可信）· 带来多少好处 **或** 得到什么结论、学到什么。实现细节不是重点——那是 design-doc（FDD）的活。
- **验收标准**：读者看完，能自己把"做了什么事情、结论是什么"复述给别人听。做不到就是写砸了。

**贯穿全文的心法**（每条都是硬要求）：
- **先直觉、后术语**：大白话 + 例子先讲明白，学名最后点一下，别开篇吓人。
- **每个论点配抓手**：一个具体数字，或一个能亲手验证的小例子；空泛的"更优 / 提升明显"没人信。
- **能图表就别大段文字**：对比表、曲线比三段话更快让人看懂——但**图 / 表下必写一句"怎么看"**。
- **简洁**：能删则删；能拆 item 就拆，每条黑体短语起头；文字尽量少。
- **准确**：一切基于真实数据或用户输入，**绝不自造**。先从现有材料中查找；关键数据仍缺失时，明确标注缺口并询问用户，不得编造（结果数字尤其）。**没收益就诚实写没收益**，别硬凑正向结论。
- **标题**：像书名一样简洁——一眼看出这份报告讲的是哪件事，别写成一句话摘要。

## 四段结构（前三段必写，第 4 段可选）

对应读者的思维顺序，两种形态各走一条：
- **有收益的改动**：我有什么痛点 → 你怎么解 → 真有效吗 → 接下来呢。
- **只有过程 / 实验**：我想验证 / 尝试什么、为什么 → 怎么做的 → 结果如何 → 学到什么、接下来呢。

### 1. 背景 = 出发点 + 为什么值得做

先说清这件事从哪来。两种开头，按实际情况选：

- **有痛点 / bad case**：用**一线原话 / 真实 bad case** 开头，让读者第一句就"对，就是这事"；多个同类 **去重、一类取一个**代表，别堆。
- **没 bad case（纯尝试 / 实验）**：说清**你做了什么尝试**，并且**为什么做这个尝试**——是什么假设、直觉、或已有线索让你觉得"这个值得试一把"。别只丢一句"试了个 X"，要写成"因为 Y，所以想试 X"，读者才知道这不是瞎试。

**为什么值得做**：分点列，落到读者在乎的维度（安全 / 成本 / 效率 / 体验 / 稳定性 / 探索价值… 按场景取），每点一句话说清机理，别只喊口号。

**（可选）招牌案例**：甩一个**带名字 + 关键数字**的真实案例先声夺人，比"某某优化明显"可信十倍，配一张对比图。没有典型案例就不写，别硬凑。

### 2. 做法 = 度量 · 例子 · 对比 · 前提 · 技术说明

克制，别写成技术炫技——**粒度只到"伪代码 + 关键步骤"级**（算法类到算子 / operator，模型 / 策略类到核心逻辑 / 关键规则即可）；再细的落地设计（数据结构、接口、实现）是 design-doc 的活。按顺序：

- **① 可感知的度量 / 目标（本段地基）**：一句话说清你在改善或探索什么、用什么量衡量，且这个量业务或问题本身能体会到含义。不必强凑成单一 min/max——多目标就点明主目标 + 附带约束。
- **② 最小例子**：造个**手算的小例子**，或（黑盒 / 模型改动）一个**最小可解释案例**，把做法演一遍——读者信"我亲眼过过的"、不信"你说的"。可渐进式（先最简、再逐步加）；例子**允许虚构**（示意用，和结果真数据不同——数据不许造）；能的话**呼应 §1 的痛点 / 尝试动机**，首尾扣起来。
- **③ 前后对比**：**同一批输入、两种做法**并排（行 = 现状 / 新法，列 = 关键指标），一眼看出差别；一张对比表胜过一段解释。
- **④ 前提 / 假设**：这法子在什么硬约束下才成立。**这些前提通常要和用户确认——缺了先问，不能自造**；主动亮出来，既划清适用边界、也把读者顾虑先答了。要和 §3 的"假设 / 局限"呼应。
- **⑤ 技术说明（后置）**：花**很小篇幅**交代**用了什么技术**（是什么问题、什么解法），别糊弄成"就是加加减减"，也别展开实现。放段末引用块 / 脚注，给懂行的人一个锚、不打扰外行。

### 3. 结果 = 范围 · 数据 · 假设 · 结果 · 结论

可信度靠"先交代清楚、再上数字"。按顺序写全：
- **范围（scope）**：测了多大范围——多少对象 / 请求 / 用户 / 样本、哪段时间、命中多少、排除了谁。范围诚实，结论才可信。
- **数据**：哪批数据、来源、口径（分母、筛选条件、**有没有对照组**）。
- **假设 / 局限**（有才写）：用了什么近似、没纳入什么、什么前提下成立——主动亮出来比被人问出来强。
- **结果**：**主指标用 §2 定义的那个**；需要时补**护栏指标 / 副作用 / 代价**（如为了 A 有没有牺牲 B），但别用一堆无关指标淹没。挑 1~2 个"读两个点就懂"的对比；配图**图下一句"怎么看"**；**不变、略升、甚至变差的结果都诚实标出**（负结果本身就是有价值的结论）；有交互产物给链接。
- **结论**：这次**沉淀了什么**——用一两句收口。验证 / 证伪了什么假设？留下什么可复用的认知（"这条路走不通，因为…"也是认知）？有收益就说清值多少，没收益就说清学到什么。**别硬凑"上不上线"的判断**，align 过再写。

### 4. 下一步 = checklist（可选）

**别急着编下一步**——只写和用户 align 过、或用户自己提出的，简短即可。有后续就用 `- [ ]` 列（验证 / 监控回滚 / 叠加优化 / 参数松紧 / 灰度 / 换个方向再试 / 长期跟踪），让读者知道不是终点；已 close、无后续则整段省略，不硬凑。

## 常见反模式（别踩）

- **开篇上术语 / 公式**：读者还没被说服"为什么要读"就被劝退。
- **尝试没说为什么试**：纯实验类报告最容易犯——只写"试了 X"，不写"因为 Y 才试 X"，读者以为你在瞎撞。
- **只有相对数、没有绝对抓手**："提升 30%"不如"从 X 降到 Y"。
- **相关性当因果 / 没对照组就宣称收益**：效果报告头号硬伤，一旦被戳穿全篇崩。
- **没收益就硬凑正向结论**：负结果 / 没动的指标也是结论，藏着或粉饰反而更掉可信度。
- **报喜不报忧**：藏着代价（某指标略升）不说，被发现则可信度崩。
- **一段话堆五个指标**：读者记不住，挑最能说明问题的一两个。
- **写成落地实现文档**：数据结构 / 接口 / 代码是 design-doc 的活，正文最多到"伪代码 + 关键步骤"。

## 写作流程

1. 先跟用户 / 源材料确认：**这次是"有收益"还是"纯过程 / 实验"、痛点原话或尝试动机、数据范围与对照口径、上线 / 实验状态、招牌案例、有没有图、前提假设、结论 / 沉淀、下一步**。缺哪块就问，别编。
2. 按四段结构起草，招式就地用（§2 的 例子 / 对比 / 前提 / 技术说明）。
3. 写完**换双眼睛重读**：每个论点都有数字 / 例子抓手吗？遮住正文、只读标题能复述吗？收益有对照支撑、没把相关当因果吗？纯尝试类说清"为什么试"和"学到什么"了吗？代价 / 负结果都诚实标了吗？够简洁吗？
4. 图表引用相对路径；交互产物给链接。
