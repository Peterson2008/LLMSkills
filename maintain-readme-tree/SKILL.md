# Maintain README Tree

把 README 体系维护成项目文档地图。根 README 是全局入口，各子目录 README 递归负责自己的局部文档。

## 核心模型

```text
根 README
├── 一级模块 A → A/README
│   ├── A 的本地文档
│   └── 子模块 A1 → A/A1/README
├── 一级模块 B → B/README
│   └── B 的本地文档
└── 全局专题文档
```

“所有文档都注册”是指：每份长期维护的文档都能从根 README 沿 Markdown 链接递归到达。不要让根 README 平铺所有深层文件。

## 所有权规则

- 根 README 负责项目定位、一级模块、全局运行入口和跨模块专题。
- 最近一层 README 负责登记本目录的长期文档和下一层 README。
- 子目录已有独立 README 时，父级只链接该 README 并用一句话说明定位，不复制其完整目录。
- README 只做地图、入口和最短必要说明；字段定义、决策理由、脚本细节、进度和实验结果留在各自的单一事实源。
- 同一文档可以从相关位置交叉引用，但必须有一个清晰的主要入口。

## 哪些内容需要注册

默认注册：

- 子项目和独立模块的 README。
- `docs/` 中长期维护的设计、决策、数据、操作和专题文档。
- 项目级 `TODO.md`、运行手册、数据字典等人工维护文档。
- 对理解或使用项目必不可少的外部文档入口。

默认排除：

- `.venv`、`node_modules`、vendor 等第三方内容。
- build、dist、缓存和生成目录。
- 临时草稿、按时间生成的备份、运行日志和一次性中间产物。
- 密钥、私人配置和只应由工具读取的内部状态。
- agent 指令文件；除非它本身也是用户需要浏览的项目文档，否则不必进入人类文档树。

存在歧义时，根据文件职责判断，并在结果中说明排除理由。

## 工作流程

1. 查找仓库级指令，以及全部项目自有的 `README.md` 和 Markdown 文档；排除第三方与生成目录。
2. 阅读根 README、子目录 README 和文档标题，识别模块边界及每份文档的最近所有者。
3. 建立“根入口 → 子 README → 本地文档”的预期树。
4. 检查：
   - 是否存在从根 README 不可达的长期文档。
   - 是否存在链接到不存在文件的相对 Markdown 链接。
   - 根 README 是否越级堆积深层实现细节。
   - 同一段说明是否在多层 README 重复。
5. 优先补链接和一句话定位；只有目录本身形成独立模块、且已有多份本地文档时，才新增子目录 README。
6. 保留仓库已有语言、标题风格和合理的 README 职责，不做无关改写。
7. 运行：

   ```bash
   python3 scripts/check_doc_tree.py /path/to/repository
   ```

8. 人工复核脚本报告。脚本只检查链接可达性，不能代替对文档职责和质量的判断。

运行命令时，以本 `SKILL.md` 所在目录为基准解析脚本路径。

## README 写法

- 开头用一两句话说明当前目录是什么、服务谁。
- 用紧凑 tree 表达稳定的目录结构；只列读者需要识别的目录和关键入口。
- tree 后用链接列表登记文档，并为每项写一句职责说明。
- 使用相对链接，确保仓库移动后仍然有效。
- 不在 tree 中罗列海量数据文件、生成产物或每个代码文件。
- 不复制子文档正文；让 README 保持可扫描。

建议骨架见 `references/readme-template.md`。

## 完成标准

- 新读者能从根 README 找到所需模块或专题。
- 每份纳入范围的长期 Markdown 文档都能从根 README 递归到达。
- 没有指向缺失文件的本地链接。
- 每层 README 只说明自己的范围，深层细节由最近的 README 管理。
- README 是文档地图，不是第二套数据字典、决策记录或 changelog。
